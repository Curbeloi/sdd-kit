# Contributing to sdd-kit

First off, thanks for your interest in contributing to **sdd-kit**! 🎉

This CLI tool is the backbone of Spec-Driven Development (SDD) — the antidote to vibe coding. Every contribution helps make AI-assisted development more structured and reliable.

> ## 🚨 The Golden Rule: We Use sdd-kit to Build sdd-kit
>
> **This project eats its own dog food.** Every feature, every bug fix, every meaningful change
> MUST start with a spec generated by `sdd spec create`. No spec, no PR. No exceptions.
>
> If we don't trust our own tool to drive our development, why should anyone else?

## The SDD-First Workflow (Mandatory)

**Every contribution that touches code MUST follow this workflow.** This is non-negotiable — we build sdd-kit using sdd-kit.

### Step 1: Generate Your Spec

Before writing a single line of code, create your specification:

```bash
# For small changes (bug fixes, minor tweaks) — tasks.md only
sdd spec create "describe the change" -1

# For medium changes (new flags, refactors) — default, requirements + tasks
sdd spec create "describe the change"

# For large changes (new commands, architectural changes) — full spec w/ design
sdd spec create "describe the change" -3
```

### Step 2: Fill Out the Spec

The generated spec files are your blueprint. Complete every section:

- **Problem statement** — What are you solving?
- **Proposed solution** — How will you solve it?
- **Technical approach** — Implementation details
- **Test cases** — What will you test?
- **Edge cases** — What could go wrong?

### Step 3: Generate Architecture (for medium/large)

For medium and large contributions, also generate the architecture view:

```bash
sdd arch
```

Review the Mermaid diagram and the interactive dashboard. Your changes must fit coherently within the existing architecture.

### Step 4: Code According to the Spec

Now you can code. Your implementation should follow the spec — not the other way around. If you discover the spec needs changes mid-implementation, **update the spec first**, then adjust the code.

### Step 5: Include Specs in Your PR

Your PR **must include** the spec files at `specs/features/<spec-name>/`. This serves as living documentation of every design decision.

```
specs/features/
├── feat-output-flag/
│   ├── requirements.md
│   └── tasks.md
├── fix-empty-dir-handling/
│   └── tasks.md
└── ...
```

### What Requires a Spec?

| Change Type | Spec Required? | Recommended Flag |
|---|---|---|
| New command | ✅ Yes | `-3` (full spec) |
| New flag/option | ✅ Yes | default (`-2`, req + tasks) |
| Bug fix | ✅ Yes | `-1` (tasks only) |
| Refactor | ✅ Yes | default (`-2`, req + tasks) |
| Typo/formatting | ❌ No | — |
| Documentation only | ❌ No | — |
| Dependency update | ❌ No | — |

### Why?

1. **Dogfooding** — We find our own bugs and UX issues before users do
2. **Quality** — Specs force you to think before you code
3. **Documentation** — Every decision is recorded, not lost in Slack
4. **Proof** — It demonstrates that SDD works in practice, on a real project

> 💡 **Pro tip**: If writing the spec feels like overkill for your change, your change might be smaller than you think — use `-1`. If it feels impossible to spec, your change might be too big — break it down.

## Getting Started

Before contributing, make sure you understand what sdd-kit does:

- **`sdd spec create`** — Generates SDD specification files; size controlled by `-1` / `-2` (default) / `-3`
- **`sdd arch`** — Generates Mermaid architecture diagrams and an interactive HTML dashboard
- It's **language-agnostic** — works with any project, any stack

If you're new to SDD, read the [README](README.md) first.

## Development Setup

### Prerequisites

- **Node.js** >= 18.0.0
- **npm** >= 9.x
- **Git**

### Installation

```bash
# 1. Fork the repo on GitHub

# 2. Clone your fork
git clone https://github.com/<your-username>/sdd-kit.git
cd sdd-kit

# 3. Install dependencies
pnpm install

# 4. Link the CLI locally for testing
pnpm link --global

# 5. Verify it works
sdd --version
```

### Running Tests

```bash
# Run all tests
pnpm test

# Run a specific test file
node --test src/path/to/file.test.js
```

> ⚠️ **All tests must pass before submitting a PR.** No exceptions.

## How to Contribute

### 🐛 Fix a Bug

1. Check [existing issues](https://github.com/Curbeloi/sdd-kit/issues) to avoid duplicates
2. Open an issue describing the bug (if one doesn't exist)
3. **Run `sdd spec create "describe fix" -1`** and fill out the spec
4. Fork → Branch → Fix → Test → PR (include spec)

### ✨ Add a Feature

1. **Open an issue first** to discuss the feature before writing code
2. Wait for approval from maintainers — this saves everyone time
3. **Run `sdd spec create "describe feature"`** (default) or `-3` for complex/architectural changes
4. **Run `sdd arch`** to validate your feature fits the architecture
5. Fork → Branch → Implement → Test → PR (include spec + architecture output)

### 📝 Improve Documentation

Documentation PRs are always welcome — no issue required. Fix typos, clarify instructions, add examples.

### 🌐 Add Translations

We welcome translations of docs and CLI messages. Open an issue to coordinate.

## Pull Request Process

1. **Generate your spec** (see [SDD-First Workflow](#the-sdd-first-workflow-mandatory)):
   ```bash
   sdd spec create "describe the change"      # default: -2 (req + tasks)
   sdd spec create "describe the change" -1   # tasks only
   sdd spec create "describe the change" -3   # full spec with design
   ```

2. **Create a branch** from `main`:
   ```bash
   git checkout -b feat/my-feature
   # or
   git checkout -b fix/bug-description
   ```

3. **Fill out the spec completely** before writing implementation code

4. **Make your changes** following the spec and our [coding standards](#coding-standards)

5. **Write/update tests** for your changes

6. **Run the full test suite** and ensure all tests pass:
   ```bash
   pnpm test
   ```

7. **Add your spec file** to the `specs/` directory

8. **Commit** using our [commit convention](#commit-convention)

9. **Push** and open a Pull Request against `main`

10. **Fill out the PR template** completely

11. **Wait for review** — maintainers will respond within 72 hours

### PR Requirements

- [ ] **SDD spec included** at `specs/features/<spec-name>/` (unless docs/deps-only change)
- [ ] Spec was generated using `sdd spec create` (not written manually)
- [ ] Implementation matches the spec
- [ ] All existing tests pass
- [ ] New tests added for new functionality
- [ ] No unnecessary dependencies added
- [ ] CLI remains language-agnostic (no framework-specific assumptions)
- [ ] Works on Node.js >= 18

> ⚠️ **PRs without specs will be rejected** (unless the change is documentation-only or a dependency update). We take dogfooding seriously.

## Coding Standards

### General Rules

- **Pure ESM** — Use `import`/`export`, no `require()`
- **No TypeScript** — This project is vanilla JavaScript (for now)
- **Async/await** over callbacks and raw promises
- **Descriptive variable names** — `specFilePath` not `sfp`
- **Functions should do one thing** — Keep them small and testable

### CLI Output

- Use **chalk** for colored output
- Use **ora** for spinners on async operations
- Always provide clear error messages with actionable suggestions
- Respect `--quiet` / `--verbose` flags if present

### Dependencies

- **Minimize new dependencies** — Every dependency is a supply chain risk
- Justify any new dependency in your PR description
- Prefer Node.js built-in modules when possible

### Tests

- Co-locate test files next to source: `myModule.js` → `myModule.test.js`
- Use Node.js built-in test runner (`node --test`)
- Test both happy paths and error cases
- Mock external calls (Anthropic API, filesystem) — don't make real API calls in tests

## Commit Convention

We follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <short description>

[optional body]

[optional footer]
```

### Types

| Type       | When to use                                |
|------------|--------------------------------------------|
| `feat`     | New feature                                |
| `fix`      | Bug fix                                    |
| `docs`     | Documentation only                         |
| `style`    | Formatting, no code change                 |
| `refactor` | Code change that neither fixes nor adds    |
| `test`     | Adding or updating tests                   |
| `chore`    | Build process, CI, tooling                 |

### Examples

```
feat(arch): add --output flag for custom diagram path
fix(spec): handle empty project directories gracefully
docs: add Spanish translation for CONTRIBUTING.md
test(spec): add tests for --size flag validation
```

## Reporting Bugs

Use the [Bug Report template](https://github.com/Curbeloi/sdd-kit/issues/new?template=bug_report.md) and include:

- **sdd-kit version** (`sdd --version`)
- **Node.js version** (`node --version`)
- **OS** (macOS, Linux, Windows)
- **Steps to reproduce**
- **Expected vs actual behavior**
- **Error output** (full stack trace if available)

## Suggesting Features

Use the [Feature Request template](https://github.com/Curbeloi/sdd-kit/issues/new?template=feature_request.md) and include:

- **Problem statement** — What pain point does this solve?
- **Proposed solution** — How would it work?
- **SDD alignment** — How does this fit the Spec-Driven Development philosophy?
- **Alternatives considered**
